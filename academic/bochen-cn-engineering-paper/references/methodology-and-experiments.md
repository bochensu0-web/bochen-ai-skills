# 方法、实验、复现与结果分析

## 先把研究问题映射为证据

建立链条：

```text
研究问题 → 可检验假设/工程目标 → 操作变量 → 数据或测试 → 指标 → 判断规则 → 结论边界
```

如果指标不能回答研究问题，先改设计，不要先跑大量实验。

## 算法与模型实验

至少固定并报告：

- 数据来源、授权、版本、规模、清洗、划分和泄漏防护
- 基线选择理由、实现来源、调参预算和公平性
- 评价指标定义及其与任务目标的关系
- 环境、硬件、软件版本、随机种子和关键超参数
- 重复次数、聚合方式、波动或置信区间
- 主结果、消融、敏感性、效率和失败案例

训练集、验证集和测试集职责要分开；不可用测试集反复调参。比较不同模型时保持数据、预处理、预算和评价一致，无法一致时明确说明。

## 系统与软件工程毕设

至少形成：需求与边界、用例/场景、架构选择、核心模块、数据模型或接口、关键实现、测试策略、部署环境、性能/安全/可靠性结果。界面截图只能证明“界面存在”，不能单独证明功能正确或性能达标。

测试分层：

- 单元或模块测试：核心逻辑是否正确
- 集成测试：模块与接口是否协同
- 系统/验收测试：用户场景是否完成
- 非功能测试：性能、稳定性、安全、可用性或资源占用

## 工程设计与自动化

明确设计输入、约束、标准、计算假设、安全系数、器件或控制方案、仿真/实验条件和验收指标。涉及法律、安全、隐私、伦理、环境或健康约束时单独列出，不只在结尾泛泛提及。

## 最小可行试验

在完整实施前做小规模验证：

1. 选最小但有代表性的数据或场景。
2. 跑通数据—方法—指标—结果全链路。
3. 检查最可能失败的依赖和时间成本。
4. 记录失败、异常和预计扩展成本。
5. 决定继续、收缩问题或切换备用方案。

## 结果分析顺序

1. **观察**：表/图中实际出现什么，给数值和范围。
2. **比较**：与基线、目标或不同条件相比如何。
3. **解释**：哪些机制可能导致，区分证据和推断。
4. **稳健性**：不同种子、子集、参数或场景是否一致。
5. **异常与失败**：哪些情况不成立，原因是否已验证。
6. **边界**：结果能支持什么，不能推广到什么。

“提高 3%”要说明是 3 个百分点还是相对提高 3%；“显著”只有在定义了统计或工程显著性并提供证据时使用。

## 复现包

建议保存：代码提交哈希、依赖清单、配置、随机种子、数据获取和处理脚本、运行命令、原始日志、结果汇总脚本、图表生成脚本、硬件与耗时。不能公开的数据或代码说明原因及可验证替代材料。

## 负面结果

负面或无明显提升不是自动失败。若设计合理、执行真实、分析清楚，可作为边界和工程决策证据。不得删掉反例后声称普遍有效，也不得挑选最好一次运行代替完整结果。
