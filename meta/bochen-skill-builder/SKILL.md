# 博晨 Skill 构建器

## 设计原则

将 Skill 写成另一位智能 Agent 可执行的工作方法，而不是一篇介绍文。只保留能改变行为的规则；假设模型已有通用常识，避免冗长背景和重复提醒。

## 不适用场景

一次性短提示、无需复用的回答偏好或已有 Skill 能稳定覆盖的任务，不应新建独立 Skill。先改进现有 Skill 或写普通项目说明。不要自动安装来源不明的社区 Skill；先审查内容、权限和许可证。

## 创建流程

1. 从用户习惯和具体请求中提取 3–6 个真实触发例子。
2. 定义 Skill 的单一核心职责、明确不负责的范围和与其他 Skill 的配合关系。
3. 选择简短、小写、连字符命名，文件夹名与 frontmatter `name` 完全一致。
4. 使用标准初始化工具创建目录和 `agents/openai.yaml`。
5. 编写只含 `name` 与 `description` 的 YAML frontmatter；把“做什么 + 何时触发”全部写入 description。
6. 用祈使式编写核心流程、判断规则、安全边界和最终自检。
7. 仅在真正需要时添加 `references/`、`scripts/` 或 `assets/`；避免重复内容。
8. 运行标准校验，并用真实用户问题做前向测试。
9. 修正触发过宽、步骤机械、输出冗长或缺少边界的问题。
10. 打包 ZIP，并在仓库根目录提供套装级 README。

## 渐进式披露

将始终需要的工作流放在 `SKILL.md`。大段领域资料放入 `references/`，确定性重复操作放入测试过的 `scripts/`，输出模板和图标放入 `assets/`。引用文件保持一层深度，并明确何时读取。核心文件控制在 500 行以内。

## 个性化标准

默认适配博晨的偏好：自然简洁中文、结论优先、少 AI 腔、少空话、机制与例子优先；面向基础较弱的大学 AI 学生，复杂主题应分步、配代码/练习、分析错误并设置复习检查点。不要把所有偏好复制到每个 Skill；通用风格放在 `$bochen-answer-style`，专项 Skill 只添加领域规则。

## 质量测试

至少检查：

- 触发描述能否覆盖真实说法，又不会抢占无关任务。
- 流程是否能处理简单、复杂、信息不足和失败场景。
- 指令是否可执行，而非“高质量、专业、全面”等空泛要求。
- 多个 Skill 是否职责重复或相互矛盾。
- 示例是否泄露预期答案，导致测试失真。
- 文件结构、YAML、命名和 UI 元数据是否通过校验。

为每个 Skill 建立 2–3 个真实任务 eval，并补充容易混淆的 should-trigger / should-not-trigger 样本。条件允许时比较“启用 Skill”与“不启用 Skill”的结果，针对实际差异迭代，而不是只检查文件格式。

## 更新与发布

更新现有 Skill 时先读取当前版本并保留有效内容，说明行为变化。不要在 Skill 文件夹中放重复 README、安装指南或变更日志；仓库级文档放根目录。上传前检查敏感信息、临时文件和许可证，记录清晰提交信息，并提供可下载 ZIP。

若用户明确要求 Skill 级 README，则将其视为人类说明文件，保持简短，不复制 `SKILL.md` 的完整规则。
